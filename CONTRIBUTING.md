# Разработка

Проект придерживается единого стиля Java и Maven. Цель правил — упростить чтение и развитие сервиса без усложнения локального запуска.

## Структура и код

- Контроллеры отвечают за HTTP; обработка файлов, управление процессами и Telegram-сценарии находятся в сервисах.
- Зависимости внедряются через конструктор, поля зависимостей — `private final`. Настройки группируются в типизированных `@ConfigurationProperties`.
- Один оператор размещается на строке; у условий и циклов используются фигурные скобки. Импорты указываются явно.
- Имена отражают роль: `Controller`, `Service`, `Handler`, `Properties`, `Dto` и `Test`.
- Для публичных API добавляется документация, когда она помогает понять контракт, ресурсы и ошибки. Комментарии объясняют неочевидные решения.
- Не игнорировать неожиданные сбои: записывать полезную диагностику без токенов, URL с токенами и содержимого файлов. Ожидаемые ветви управления описывать явно.
- Интерфейс выделяется там, где есть несколько реализаций, внешняя граница или реальная потребность в подмене; отдельная пара интерфейс/реализация для каждого класса не обязательна.

## Настройки и проверки

- Новые параметры описываются в README: имя, значение по умолчанию, назначение и пример запуска.
- Тесты проверяют наблюдаемое поведение, обработку ошибок и сохранность ресурсов. Тесты FFmpeg запускаются при `RUN_FFMPEG_TESTS=true`.
- Полная проверка: `mvn clean verify` с Java 25 и установленными `ffmpeg`/`ffprobe`. Для тестов реального кодирования предварительно установите `RUN_FFMPEG_TESTS=true`.
- Токены и пользовательские медиа не коммитятся. При изменении Telegram API сохраняйте возможность запуска REST без токена.

Spring Boot 4 использует Spring TestContext с JUnit 6; проект намеренно остаётся на JUnit 5 по исходному требованию, поэтому API-тесты запускают Spring-контекст явно, без SpringExtension.
